# Домашнее задание к занятию «Микросервисы: подходы»

## Задача 1. Обеспечить разработку

Для организации процесса разработки и поставки я предлагаю использовать связку GitLab SaaS, GitLab Runner, HashiCorp Vault и Docker Registry.

GitLab SaaS выступает как облачная система, в которой размещаются Git-репозитории, пайплайны CI/CD, шаблоны сборок, настройки окружений и базовые средства управления доступом. Под каждый микросервис создаётся отдельный Git-репозиторий. Такой подход упрощает разграничение прав, версионирование, настройку пайплайнов и независимые релизы сервисов.

Разработчик отправляет изменения в репозиторий, после чего GitLab по событию `push`, `merge request`, `tag` или по другому правилу запускает соответствующий пайплайн. Кроме автоматического запуска, GitLab позволяет запускать сборки вручную через интерфейс, передавая переменные окружения и параметры выполнения. Это закрывает требование запуска сборки по кнопке с указанием параметров.

Настройки сборок удобно хранить в файле `.gitlab-ci.yml` внутри каждого репозитория. За счёт этого конфигурация версионируется вместе с кодом, а изменения в логике сборки проходят через тот же процесс ревью, что и код приложения. Для повторного использования можно вынести типовые этапы в отдельный шаблонный репозиторий и подключать их через `include`. Это позволяет создавать единые шаблоны для Java-, Python-, Node.js- и других сервисов, а затем переопределять только различающиеся части.

Если из одного репозитория нужно собирать несколько конфигураций, это можно реализовать через разные job в одном пайплайне, через `rules`, через матрицы переменных и через отдельные stages. Например, можно отдельно собирать production-образ, debug-образ, образ для feature-ветки и пакет для интеграционного тестирования. Для каждого варианта можно привязать свои переменные, правила запуска и окружения.

Кастомные шаги в GitLab CI описываются прямо в пайплайне. Это может быть генерация артефактов, запуск линтеров, security scanning, миграции схем, подготовка тестовых данных или публикация образов. Если стандартных контейнеров недостаточно, можно использовать собственные Docker-образы для сборки проектов. Это особенно удобно, когда нужно зафиксировать конкретные версии JDK, Node.js, Python, Terraform, kubectl, helm и вспомогательных утилит.

Для выполнения пайплайнов предлагаю развернуть GitLab Runner на собственных серверах компании. Это соответствует требованию использования собственных агентов сборки и даёт контроль над производительностью, сетевым доступом и безопасностью. Часть раннеров можно выделить под обычные сборки, часть под тяжёлые интеграционные тесты, часть под деплой. При необходимости раннеры можно масштабировать горизонтально.

Параллельный запуск нескольких сборок и тестов в GitLab реализуется штатно. Несколько job одного пайплайна могут выполняться одновременно, а также параллельно могут идти пайплайны разных сервисов. Для ускорения тестирования можно разбивать тесты по группам и запускать их параллельно в отдельных job. Это особенно полезно для микросервисной среды, где сервисов много и время обратной связи критично.

Для хранения секретов я предлагаю использовать HashiCorp Vault с интеграцией в GitLab CI. В простом варианте можно использовать защищённые переменные GitLab, но для production-сценария Vault надёжнее, потому что позволяет централизованно хранить секреты, выдавать их динамически и разграничивать доступ по ролям и политикам. В пайплайне секреты будут подставляться только на время выполнения задачи без хранения в репозитории и без жёсткого прописывания в конфигурации.

Артефакты сборки и контейнерные образы удобно хранить в GitLab Container Registry или в отдельном Docker Registry, если в компании уже принят выделенный реестр образов. После успешной сборки образ публикуется в registry, а следующий этап пайплайна разворачивает новую версию в нужное окружение.

Итоговое взаимодействие компонентов выглядит так: разработчик вносит изменения в отдельный репозиторий сервиса, GitLab по событию запускает пайплайн, GitLab Runner выполняет сборку в нужном Docker-образе, получает секреты из Vault, запускает тесты, публикует артефакты и контейнерный образ в registry, после чего запускается этап поставки в тестовую или промышленную среду.

Обоснование выбора следующее. GitLab закрывает практически все требования одной платформой и уменьшает количество отдельных интеграций. Он поддерживает Git, облачное размещение, гибкие пайплайны, ручной и автоматический запуск, шаблоны, безопасную работу с переменными, собственные раннеры и хорошую масштабируемость. Vault логично дополняет решение как специализированное и безопасное хранилище секретов. В результате получается достаточно простая, современная и промышленная схема CI/CD для микросервисной архитектуры.

## Задача 2. Логи

Для централизованного сбора и анализа логов я предлагаю использовать стек Elastic: Filebeat или Fluent Bit на узлах, Kafka как промежуточную очередь для гарантированной доставки, Elasticsearch как центральное хранилище и Kibana как интерфейс поиска и анализа.

Основной принцип такой: приложения в микросервисах не пишут логи в локальные файлы в произвольном формате, а выводят их в `stdout` и `stderr`. Это минимизирует требования к самим приложениям и хорошо соответствует контейнерной среде. Далее логи считываются агентом на хосте, например Filebeat или Fluent Bit, который собирает stdout контейнеров и системные журналы.

Чтобы обеспечить гарантированную доставку логов до центрального хранилища, я предлагаю использовать Kafka как буфер между агентами и Elasticsearch. Агент отправляет записи в Kafka, Kafka сохраняет их до обработки, а далее Logstash или Kafka Connect передаёт события в Elasticsearch. Такой подход устойчивее прямой отправки, потому что временная недоступность Elasticsearch не приводит к немедленной потере логов. Очередь сглаживает пики нагрузки и позволяет переживать кратковременные сбои.

Elasticsearch используется как центральное хранилище и поисковый движок. В нём удобно индексировать логи по времени, сервису, окружению, уровню логирования, trace id, hostname и другим полям. Это позволяет быстро фильтровать события, строить запросы и искать аномалии.

Kibana предоставляет пользовательский интерфейс для разработчиков и инженеров эксплуатации. Через неё можно выполнять поиск по логам, применять фильтры, сохранять поисковые запросы, настраивать временные диапазоны и делиться ссылками на сохранённые выборки. Это напрямую закрывает требования по доступу разработчиков к поиску и по возможности передавать ссылку на сохранённый поиск.

В такой архитектуре взаимодействие компонентов выглядит так: сервисы выводят логи в stdout, Filebeat или Fluent Bit на каждом хосте забирает эти логи и отправляет их в Kafka, затем Logstash или коннектор считывает сообщения из Kafka и индексирует их в Elasticsearch, после чего пользователи работают с логами через Kibana.

Обоснование выбора следующее. Elastic Stack является одним из самых распространённых решений для централизованного логирования, хорошо подходит под микросервисную архитектуру и даёт мощный полнотекстовый поиск. Использование stdout не требует сложной доработки приложений. Добавление Kafka повышает надёжность доставки и устойчивость всей схемы. Kibana обеспечивает удобный интерфейс для разработчиков, аналитиков и администраторов без необходимости давать им прямой доступ к серверам.

Если система не очень крупная и требования к гарантированной доставке мягче, Kafka можно убрать и отправлять логи напрямую в Elasticsearch. Но для крупной компании и большого количества микросервисов наличие промежуточной очереди выглядит более оправданным.

## Задача 3. Мониторинг

Для мониторинга состояния хостов и сервисов я предлагаю использовать Prometheus, exporters для хостов и приложений, а также Grafana для визуализации и анализа.

Prometheus будет выступать как центральная система сбора метрик. Он по расписанию опрашивает все источники метрик и сохраняет значения во временные ряды. Такой подход хорошо подходит для динамической микросервисной среды, особенно если сервисы разворачиваются в контейнерах или оркестраторе.

Для сбора метрик с хостов используется Node Exporter. Он предоставляет метрики по CPU, RAM, файловым системам, дискам, сетевым интерфейсам и другим системным ресурсам. Таким образом закрывается требование по наблюдению за состоянием всех хостов.

Для метрик потребления ресурсов отдельными сервисами можно использовать cAdvisor, kube-state-metrics и метрики контейнерной платформы, если система работает в Kubernetes. Если микросервисы запущены на обычных виртуальных машинах или Docker-host, то cAdvisor позволит собирать метрики по CPU, памяти, файловой системе и сети для каждого контейнера. Это закрывает требование по мониторингу ресурсов на уровне каждого сервиса.

Специфичные для сервиса метрики должны экспортироваться самим приложением в формате Prometheus. Например, это могут быть количество запросов, длительность обработки, число ошибок, глубина очереди, количество активных сессий, бизнес-метрики и любые внутренние показатели. Для популярных языков и фреймворков уже существуют готовые клиентские библиотеки Prometheus, поэтому внедрение обычно несложное.

Grafana используется как основной пользовательский интерфейс. В ней можно выполнять запросы к Prometheus, строить графики, агрегировать данные по сервисам, окружениям и инстансам, а также создавать отдельные панели и полноценные дашборды для эксплуатации, разработки и менеджмента. Это полностью соответствует требованиям по пользовательскому интерфейсу, запросам и настройке панелей.

Взаимодействие компонентов выглядит так: на каждом хосте работает Node Exporter, на контейнерных узлах работает cAdvisor, сами приложения публикуют метрики на HTTP endpoint, Prometheus регулярно собирает все эти данные, а Grafana подключается к Prometheus и отображает метрики в удобном виде.

Обоснование выбора следующее. Prometheus стал фактическим стандартом мониторинга облачных и микросервисных систем. Он хорошо масштабируется, поддерживает удобный язык запросов PromQL, имеет большое количество готовых exporters и легко интегрируется с Grafana. Grafana, в свою очередь, даёт гибкий и понятный интерфейс для построения дашбордов и анализа состояния системы. Такая связка покрывает как инфраструктурный мониторинг, так и мониторинг прикладных метрик.

## Итог

Для разработки и поставки предлагается использовать GitLab SaaS, GitLab Runner, Vault и Docker Registry. Для логов подходит стек Filebeat или Fluent Bit, Kafka, Elasticsearch и Kibana. Для мониторинга оптимальна связка Prometheus, Node Exporter, cAdvisor и Grafana.

Все три решения хорошо сочетаются между собой, широко применяются в production-среде и подходят для крупной компании, которая развивает микросервисную архитектуру и хочет получить управляемую, масштабируемую и безопасную инфраструктуру.
