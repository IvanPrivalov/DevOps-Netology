# Домашнее задание к занятию «Микросервисы: принципы»

## Задача 1. API Gateway

Для роли API Gateway можно рассмотреть несколько решений.

### 1. Kong Gateway

- умеет маршрутизировать запросы к нужным сервисам по конфигурации;
- поддерживает проверку аутентификации через JWT, OAuth2, OpenID Connect и другие механизмы;
- умеет выполнять терминацию HTTPS;
- хорошо подходит именно под роль API Gateway, а не просто reverse proxy;
- имеет развитую систему плагинов.

### 2. NGINX

- умеет маршрутизировать запросы по заданным правилам;
- поддерживает HTTPS termination;
- может участвовать в проверке аутентификации, но для сложных сценариев часто требует дополнительных модулей или внешней логики;
- очень стабилен и быстр;
- чаще используется как reverse proxy и балансировщик, чем как полноценный API Gateway.

### 3. Traefik

- умеет маршрутизировать запросы по конфигурации;
- поддерживает HTTPS termination;
- может работать с аутентификацией через middleware и внешние сервисы;
- особенно удобен в Docker- и Kubernetes-среде;
- хорошо подходит для динамической инфраструктуры.

### Выбор

Для этой задачи я бы выбрал **Kong Gateway**.

### Обоснование

По условиям задания нужен инструмент, который без лишних доработок умеет делать три вещи: направлять запросы в нужный сервис, проверять аутентификационные данные и завершать HTTPS-соединение. Kong закрывает эти требования наиболее прямо.

NGINX для такой задачи тоже можно использовать, но он больше подходит как универсальный reverse proxy. Если строить на нём именно API Gateway, часто приходится отдельно продумывать часть функций, которые в Kong уже предусмотрены.

Traefik удобен и современен, особенно если инфраструктура полностью завязана на контейнеры. Но если смотреть именно на классическую роль API Gateway с акцентом на управление доступом и централизованную обработку запросов, Kong выглядит сильнее.

### Итог

Оптимальным решением для API Gateway будет **Kong Gateway**, потому что он лучше других подходит под требования задания и не требует лишней обвязки.

## Задача 2. Брокер сообщений

Для брокера сообщений можно рассмотреть несколько вариантов.

### 1. RabbitMQ

- поддерживает кластеризацию;
- умеет хранить сообщения на диске;
- обеспечивает высокую скорость работы для большинства прикладных задач;
- не ограничивает формат полезной нагрузки сообщений;
- поддерживает разграничение прав доступа;
- достаточно прост в эксплуатации и администрировании;
- хорошо подходит для корпоративных интеграций.

### 2. Apache Kafka

- поддерживает кластеризацию;
- хранит сообщения на диске;
- обеспечивает очень высокую производительность;
- подходит для разных форматов сообщений;
- умеет разграничивать доступ;
- хорошо работает при больших потоках событий;
- сложнее в сопровождении и администрировании, чем RabbitMQ.

### 3. NATS JetStream

- поддерживает кластеризацию;
- умеет сохранять сообщения на диске;
- работает очень быстро;
- может передавать сообщения в разных форматах;
- поддерживает разграничение доступа;
- относительно прост по архитектуре, но в типовых корпоративных системах используется реже;
- чаще выбирается там, где важны скорость и лёгкость.

### Выбор

Для этой задачи я бы выбрал **RabbitMQ**.

### Обоснование

По условиям задания нужен не просто быстрый брокер, а решение, которое сочетает надёжность, сохранность сообщений, контроль доступа и удобство в эксплуатации. RabbitMQ даёт самый ровный баланс по этим требованиям.

Kafka выигрывает по производительности и особенно хороша для больших потоков событий и аналитических платформ. Но в обычной корпоративной системе она часто оказывается сложнее в сопровождении, чем это действительно нужно.

NATS JetStream тоже интересный вариант, особенно если важны лёгкость и скорость. Но RabbitMQ выглядит более привычным и предсказуемым решением для стандартных интеграционных задач внутри крупной компании.

### Итог

Для роли брокера сообщений оптимальным выбором будет **RabbitMQ**, потому что он сочетает надёжность, хранение сообщений, разграничение доступа и сравнительно простую эксплуатацию.
